1.5	Resource Requirement
	This section outlines the essential hardware and software resources required to develop, deploy, and maintain the SenioCare mobile application and AI-driven elderly healthcare assistant system. The system relies on GPU-accelerated computing infrastructure for local LLM inference, modern multi-agent AI frameworks, cloud-hosted databases, and a cross-platform mobile frontend to ensure responsive, real-time operation and a warm, personalized user experience.
❖ Hardware Requirements
To support real-time AI-powered healthcare assistance, multi-model LLM inference, image analysis, and responsive mobile interactions, the system requires the following hardware components:
• Server Infrastructure:
A GPU-enabled server setup is required to handle computationally intensive tasks such as running multiple Large Language Models (LLMs) simultaneously via Ollama for the multi-agent pipeline and vision-based image analysis. The minimum specifications for local development and testing include a multi-core processor (e.g., 8 cores or more), 16 GB of system RAM, a dedicated GPU with at least 8 GB of VRAM (e.g., NVIDIA RTX 3060 or higher) for loading models such as Gemma4 (~9.6 GB), olmocr2:7b-q8 (~7.7 GB), and Llama 3.2-Vision (~7.9 GB), and at least 256 GB of SSD storage for model weights and application data. For production deployment, a smaller quantized model will be selected to reduce GPU and memory requirements, enabling hosting on free-tier cloud platforms. During development and experimentation phases, Google Colab with GPU runtime is utilized to test larger models such as Gemma 4 that exceed local hardware capabilities. The general-purpose backend requires no dedicated server infrastructure and is deployed on any free serverless web service platform.
• Mobile Device Requirements:
A smartphone or tablet running Android or iOS is required for end users. The minimum device specifications include 4 GB of RAM for smooth application performance, a stable internet connection for accessing backend and AI services, a device camera for uploading and analyzing medical images (medication boxes and medical reports), and a minimum of 64 GB storage capacity for storing application data, cached content, and medical documents.
• Storage:
The system utilizes Neon PostgreSQL, a serverless cloud-hosted PostgreSQL service, as the primary persistent storage solution for the AI backend. Three logical databases are maintained on Neon: the session database (managed by Google ADK's DatabaseSessionService for conversation persistence and user state), the memory service database (for cross-session context recall), and the application database (storing health data including meals, exercises, drug-food interactions, disease symptoms, dietary rules, food allergens, and analyzed medical reports). Cloud-hosted PostgreSQL provides automatic backups, high availability, connection pooling, and seamless scalability as user demand increases, eliminating the need for self-managed database infrastructure.
Additionally, the general-purpose backend utilizes a MongoDB Atlas cluster as its primary database, hosting the SenioCare database with collections for users, elders, caregivers, service providers, medicines, daily medicines, medicine logs, medical documents, and services. Cloudinary is used as a cloud-based media storage solution for uploading medical images and generating secure image URLs before sending them to the backend server for storage and AI analysis.
• Network Infrastructure:
A reliable internet connection with reasonable bandwidth is essential to support real-time data transmission between the Flutter mobile application and the two independent backend servers: the FastAPI AI agent server (for healthcare conversations, image analysis, and profile synchronization) and the Python/FastAPI general backend (for user authentication, registration, and application-level data). The Flutter app communicates with the FastAPI AI server via RESTful HTTP and Server-Sent Events (SSE) for streaming agent responses, and with the general backend via RESTful APIs for authentication and data management. Network stability is critical for maintaining a seamless conversational experience, particularly during multi-turn healthcare dialogues and medical report image uploads. The system also requires outbound internet access from the AI server for SerpAPI-based web search, YouTube video search, and medical information retrieval from trusted sources, as well as outbound access from the general backend for Google OAuth token verification and AI profile initialization on the Replit-hosted AI service.

❖ Software Requirements

The project requires a comprehensive, multi-layered software stack that supports cross-platform mobile development, multi-agent AI orchestration, local LLM inference, real-time healthcare tool execution, image-based medical analysis, and secure data management. The software tools and technologies include:
• Flutter:
Used as the primary framework for cross-platform mobile app development, enabling a consistent user experience on both Android and iOS devices from a single codebase. Flutter's rich widget library, responsive design capabilities, and support for RTL (right-to-left) Arabic layouts make it ideal for building an accessible, elderly-friendly interface that displays AI-generated healthcare responses, meal recommendations, exercise plans, medication information, and medical report analyses. The Flutter frontend communicates directly with the FastAPI AI server for all healthcare-related interactions and independently with the general backend for authentication and application services. Bloc state management is used throughout the application for managing application states and reactive UI updates, providing a predictable, testable architecture for handling complex user interaction flows.
• Dart:
The programming language behind Flutter, used for implementing the frontend logic, managing application state, handling user interactions, and making HTTP requests to the backend services. Dart enables fast development cycles with hot reload, strong type safety, and smooth integration with RESTful APIs. The Dio HTTP client library is used as the primary networking layer, extended with Retrofit for type-safe API communication, pretty_dio_logger for request/response debugging, and dio_cache_interceptor for response caching to reduce redundant network calls.
• Python:
The primary programming language for both backend servers, chosen for its extensive ecosystem of AI/ML libraries, asynchronous capabilities, and compatibility with Google's Agent Development Kit. Python 3.10+ is required for the use of modern type annotations, pattern matching, and async/await patterns throughout the codebase.
• FastAPI:
Used as the REST API server framework for both the AI backend and the general backend. For the AI server, FastAPI provides high-performance asynchronous request handling, automatic OpenAPI/Swagger documentation generation (accessible at /docs), request validation via Pydantic models, and native support for Server-Sent Events (SSE). FastAPI serves both the Google ADK agent endpoints (for running the multi-agent pipeline) and custom endpoints for session management, chat history retrieval, user profile synchronization, and image analysis. For the general backend, FastAPI handles user authentication, registration, profile management, medication tracking, and service coordination. Uvicorn is used as the ASGI server to run both FastAPI applications in production.
• Google Agent Development Kit (ADK):
The core AI orchestration framework that powers SenioCare's 3-agent sequential pipeline. ADK provides the SequentialAgent abstraction for chaining the Orchestrator, Feature, and Formatter agents, along with session management (DatabaseSessionService), tool registration, state scoping (user-scoped, session-scoped, invocation-scoped), and lifecycle callbacks (before_agent and after_agent hooks). ADK integrates with Ollama via the LiteLLM abstraction layer, enabling the use of locally-hosted open-source LLMs without cloud API dependencies for core AI functionality.
• LLM Models (via Ollama):
	o Gemma 4 (Development/Testing):
	Used as the primary reasoning model for all three agents in the sequential pipeline — the Orchestrator Agent (safety screening, intent classification, and task planning), the Feature Agent (tool calling and decision-making), and the Formatter Agent (Egyptian Arabic response generation). Served locally via Ollama on port 11434, integrated through LiteLLM's ollama_chat provider. It was used during development and experimentation phases via Google Colab with GPU runtime to evaluate the pipeline's performance with a more capable model. Gemma 4 serves as a benchmark for comparing response quality and is planned for production use once a sufficiently powerful server is available for deployment.
	o richardyoung/olmocr2:7b-q8:
	A specialized OCR-focused vision model used exclusively for the Medication Image Analysis feature. This model extracts medication names, active ingredients, dosages, manufacturer information, and expiry dates from photographs of medication boxes and packages. The 8-bit quantized variant (q8) reduces memory usage while maintaining OCR accuracy.
	o Llama 3.2-Vision:
	A multimodal vision-language model used for the Medical Report Analysis feature. This model performs two-pass analysis: first extracting structured data (lab values, test types, findings) from medical report images, then evaluating the health situation and classifying severity as NORMAL, ATTENTION, or CRITICAL. A rule-based severity fallback system cross-validates the AI's assessment against known clinical thresholds for patient safety.
• Database Systems:
	o Neon PostgreSQL (AI Backend):
	A serverless, cloud-hosted PostgreSQL service used for all AI backend data persistence. Accessed via the psycopg2 driver (synchronous, for health data tools) and asyncpg driver (asynchronous, for ADK session management). The database stores 8 tables: meals (19 records), condition_dietary_rules (5 conditions), drug_food_interactions (20 records), disease_symptoms (15 diseases), disease_precautions, food_allergens, exercises (by mobility level), and medical_reports (historical analysis results). Database initialization is idempotent, with seed data loaded from JSON files on application startup.
	o MongoDB Atlas (General Backend):
	A cloud-hosted NoSQL document database used by the general backend for all non-AI application data. Accessed via the motor library (AsyncIOMotorClient) for fully asynchronous database operations. The SenioCare database hosts the following collections: users, elders, caregivers, serviceproviders, medicines, daily_medicines, medicine_logs, medical_documents, and services. MongoDB's flexible document schema accommodates the varying data structures across different user roles and medical record types without requiring rigid relational schemas.
• External APIs and Services:
	o SerpAPI:
	Provides programmatic access to Google Search, YouTube Search, and medical information retrieval. Used by three tools in the Feature Agent: search_web (general web search with BeautifulSoup content extraction), search_youtube (exercise and recipe video discovery with duration filtering and embed URL generation), and search_medical_info (medical queries restricted to trusted sources including Mayo Clinic, WebMD, NIH, WHO, CDC, MedlinePlus, Healthline, and Cleveland Clinic). A local knowledge base fallback is implemented for when API access is unavailable.
	o Ollama Server:
	A local LLM inference server running on localhost:11434, providing a REST API for model management and text/image generation. Ollama handles model loading, GPU memory management, and concurrent inference requests for all three pipeline agents and both image analysis modules.
	o Google OAuth API:
	Used for secure user authentication using Google accounts. The Flutter client sends a Google ID token to the general backend, which verifies the token via the Google Identity Platform before issuing a server-side JWT for subsequent authenticated requests.
	o Cloudinary API:
	Used for uploading medical images (medication box photos and medical report scans) and generating secure image URLs. The Flutter app uploads images to Cloudinary first, then sends the resulting secure URLs to the backend server for persistent storage and forwarding to the AI server for analysis.
	o AI Profile Initialization Service:
	A Replit-hosted service endpoint at https://senio-care--ayasserhashem.replit.app/set-user-profile/{user_id} is called via httpx on every new user registration from the general backend to initialize the user's AI profile in the SenioCare AI system, ensuring the multi-agent pipeline has access to the user's health data from their first interaction. Errors during this initialization are silently ignored to prevent registration failures.
	o Render:
	A cloud platform used for deploying the general backend server, providing managed hosting, automatic deployments, and SSL termination.

• Authentication and Security:
	Authentication is handled through Google OAuth 2.0 across the entire system. On the mobile application side, the google_sign_in Flutter package initiates the Google sign-in flow and obtains a Google ID token. This token is sent to the general backend's /auth/google endpoint, where the server verifies it using the Google Identity Platform via the google-auth library. Upon successful verification, the backend issues an HS256-signed JWT containing the user's id, email, and role. All subsequent API requests to the general backend (except /auth/google and the root endpoint /) are protected by an HTTPBearer dependency that validates this JWT. The system supports three user roles — elder, caregiver, and serviceProvider — though role-based access control is not currently enforced on individual endpoints; any valid token can access any protected route. Sensitive credentials on the mobile side are stored locally using flutter_secure_storage. The AI backend manages user identity independently through user_id-scoped session state within ADK's session management system, with user profiles pushed from the general backend via the /set-user-profile endpoint during registration.
